# Aether Oracle - технический файл проекта и инструкция переноса

> Этот файл описывает текущую структуру проекта Aether Oracle и порядок его развёртывания без привязки к Render. Он предназначен для восстановления проекта на VPS, отдельном сервере, Docker-хосте или другой платформе с Node.js и PostgreSQL.

Дата подготовки: 13 августа 2026 года  
Основной репозиторий: [github.com/Shalis519/Oracle2.1](https://github.com/Shalis519/Oracle2.1)  
Текущая ветка: `main`

---

## 1. Назначение проекта

Aether Oracle - русскоязычная эзотерическая веб-платформа с личными расчётами по западной астрологии, Бацзы, Фэншуй, Ци Мэнь, оракулу дня и связанным активациям.

Все пользовательские тексты должны оставаться на русском языке. В интерфейсе используются обычные короткие дефисы `-`, а для названий активаций применяется единый термин **«Активизация»**.

Проект использует личные данные пользователя, поэтому при переносе особенно важно сохранить секреты Clerk, подключение к PostgreSQL, настройки CORS, домен frontend и резервную копию базы данных.

## 4. Как работает production-архитектура

Проект состоит из двух отдельных сервисов.

Frontend собирается Vite в статические файлы. После сборки результат находится в `artifacts/web/dist/public`. Эти файлы можно размещать на любом static hosting: Nginx, Caddy, Cloudflare Pages, Netlify, отдельный object storage или собственный Node static server.

API собирается esbuild в `artifacts/api-server/dist/index.mjs` и запускается командой `node --enable-source-maps ./dist/index.mjs`. API должен иметь доступ к PostgreSQL и секретным переменным Clerk.

```text
Пользователь
    │
    ▼
Frontend static hosting
    │  VITE_API_URL
    ▼
Express API :PORT
    │
    ├── PostgreSQL через DATABASE_URL
    └── Clerk через CLERK_SECRET_KEY
```

Для production рекомендуется использовать один основной домен frontend и отдельный API-домен, например:

```text
https://oracle.example.com
https://api.oracle.example.com
```

Если frontend и API находятся на разных доменах, API должен разрешать frontend-домен в CORS. Нельзя оставлять широкое разрешение всех доменов в production без необходимости.

## 5. Переменные окружения

### 5.1. API-сервис

| Переменная | Обязательность | Назначение |
|---|---:|---|
| `PORT` | Да | Порт Express API. Платформа должна передать его в окружение. |
| `DATABASE_URL` | Да | Полная строка подключения к PostgreSQL. |
| `CLERK_SECRET_KEY` | Да | Секретный серверный ключ Clerk. Никогда не помещать во frontend. |
| `CLERK_PUBLISHABLE_KEY` | Обычно да | Publishable key, используемый серверной Clerk-инфраструктурой. |
| `ADMIN_SECRET` | Для защищённой студии | Код доступа к административным функциям Oracle Studio. |
| `NODE_ENV` | Рекомендуется | Для production установить `production`. |
| `LOG_LEVEL` | Необязательно | Уровень логирования Pino, например `info`. |
| `REPLIT_DOMAINS` | Только если нужен Replit | Не требуется для обычного VPS или Docker-развёртывания. |

### 5.2. Frontend-сервис

Vite встраивает переменные `VITE_*` в frontend во время сборки. Изменение этих переменных требует новой frontend-сборки.

| Переменная | Обязательность | Назначение |
|---|---:|---|
| `VITE_API_URL` | Да при раздельных доменах | Полный адрес API, обычно с суффиксом `/api`, например `https://api.oracle.example.com/api`. |
| `VITE_CLERK_PUBLISHABLE_KEY` | Да | Публичный ключ Clerk. Его можно использовать во frontend. |
| `VITE_CLERK_PROXY_URL` | Если используется Clerk proxy | Адрес proxy Clerk, если он нужен для текущей конфигурации домена. |
| `BASE_PATH` | Необязательно | Базовый путь Vite. Для корня сайта оставить `/`. |
| `API_PORT` | Только локальная разработка | Порт API, на который Vite проксирует `/api`. По умолчанию `8080`. |

### 5.3. Правила безопасности

Никогда не коммитить `.env`, `DATABASE_URL`, `CLERK_SECRET_KEY` или `ADMIN_SECRET` в GitHub. Для переноса использовать секретное хранилище выбранной платформы, файл `.env` только на сервере или Docker secrets.

Публичными считаются только ключи с префиксом `VITE_`, но даже их следует задавать через настройки окружения, а не фиксировать в исходном коде.

## 6. Установка проекта на новом сервере

Требования к серверу:

- Linux x86_64 или совместимая среда;
- Node.js 24;
- pnpm;
- PostgreSQL 14 или новее;
- DNS-домены и HTTPS-сертификат для production;
- минимум 1-2 GB RAM для обычной работы API и сборки frontend.

Пример установки:

```bash
git clone https://github.com/Shalis519/Oracle2.1.git
cd Oracle2.1
git checkout main
corepack enable
corepack prepare pnpm@latest --activate
pnpm install --frozen-lockfile
```

Если на сервере используется Node Version Manager:

```bash
nvm install 24
nvm use 24
corepack enable
```

Перед запуском необходимо создать PostgreSQL-базу и задать `DATABASE_URL`.

## 7. Создание и обновление базы данных

Схема хранится в `lib/db/src/schema/`, конфигурация Drizzle - в `lib/db/drizzle.config.ts`.

Для первоначального применения схемы:

```bash
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/DBNAME?sslmode=require'
pnpm --filter @workspace/db run push
```

Для текущего проекта это особенно важно: если схема не применена, API может остановиться с ошибкой отсутствующей таблицы, например `relation does not exist`.

После изменения схемы:

```bash
pnpm --filter @workspace/db run push
```

Перед операциями с базой данных обязательно создать резервную копию:

```bash
pg_dump "$DATABASE_URL" --format=custom --file=aether-oracle-$(date +%Y%m%d-%H%M).dump
```

Восстановление резервной копии:

```bash
pg_restore --clean --if-exists --dbname="$DATABASE_URL" aether-oracle-YYYYMMDD-HHMM.dump
```

Команда `push-force` существует, но использовать её без резервной копии нельзя:

```bash
pnpm --filter @workspace/db run push-force
```

Если меняется только TypeScript-код, применять Drizzle push не требуется. Если меняется OpenAPI-схема, нужно обновить сгенерированные типы согласно процедуре проекта.

## 8. Сборка и запуск API

Production-сборка API:

```bash
pnpm --filter @workspace/api-server run build
```

Результат:

```text
artifacts/api-server/dist/index.mjs
```

Запуск:

```bash
cd artifacts/api-server
NODE_ENV=production PORT=8080 node --enable-source-maps ./dist/index.mjs
```

Для systemd пример сервиса:

```ini
[Unit]
Description=Aether Oracle API
After=network.target

[Service]
Type=simple
User=aether
WorkingDirectory=/srv/aether-oracle
EnvironmentFile=/etc/aether-oracle/api.env
ExecStart=/usr/bin/node --enable-source-maps /srv/aether-oracle/artifacts/api-server/dist/index.mjs
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Проверка API:

```bash
curl -i http://127.0.0.1:8080/api/healthz
```

Ожидаемый ответ:

```json
{"status":"ok"}
```


Для Nginx пример server block:

```nginx
server {
    listen 443 ssl http2;
    server_name oracle.example.com;

    root /srv/aether-oracle/artifacts/web/dist/public;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080/api/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Если используется отдельный API-домен, установить `VITE_API_URL=https://api.oracle.example.com/api` перед frontend-сборкой и разрешить `https://oracle.example.com` в CORS API.

## 10. Локальная разработка

В одном терминале запустить API:

```bash
pnpm --filter @workspace/api-server run dev
```

Команда development API устанавливает `NODE_ENV=development`, использует порт `8080`, собирает API и запускает его.

Во втором терминале запустить frontend:

```bash
pnpm --filter @workspace/web run dev
```

Vite работает на порту `22333`, если не задан другой `PORT`. Вне Replit Vite автоматически проксирует `/api` на `http://localhost:${API_PORT ?? 8080}`.

Для локальной разработки обычно достаточно:

```env
# API
PORT=8080
DATABASE_URL=postgresql://...
CLERK_SECRET_KEY=sk_test_...
CLERK_PUBLISHABLE_KEY=pk_test_...
ADMIN_SECRET=...
NODE_ENV=development

# Frontend
VITE_API_URL=http://localhost:8080/api
VITE_CLERK_PUBLISHABLE_KEY=pk_test_...
```

Не использовать production-ключи Clerk в локальной разработке, если для этого нет специальной необходимости.

## 11. Авторизация и Oracle Studio

Авторизация построена на Clerk.

API получает пользователя через Clerk middleware и `getAuth(req)`. Для ручного Bearer-токена используется совместимый `verifyToken` из `@clerk/backend`. После подтверждения Clerk ID пользователь создаётся или находится в локальной таблице пользователей PostgreSQL.

Защищённые маршруты проверяют наличие локального пользователя и его роль. Oracle Studio дополнительно использует `ADMIN_SECRET`. Значение кода должно быть одинаково задано в API production-окружении и в пользовательском интерфейсе входа, если frontend запрашивает код через API.

При переносе проверить:

1. домен frontend добавлен в разрешённые домены Clerk;
2. callback и allowed origins Clerk соответствуют новому домену;
3. `CLERK_SECRET_KEY` и `VITE_CLERK_PUBLISHABLE_KEY` относятся к одной Clerk-инстанции;
4. API и frontend используют одну и ту же базу пользователей;
5. после входа запрос `/api/profile` возвращает профиль;
6. запрос к `/api/healthz` доступен без авторизации;
7. Oracle Studio открывается только с корректным кодом и ролью.

## 13. Расчётные модули и важные правила

### Западная астрология

Backend-модуль `astrology.ts` рассчитывает натальную карту, дома Плацидуса, планеты, аспекты и транзитные положения. Ретроградность планет хранится в полях natal/transit данных.

Натальная карта зависит от даты, времени, координат и часового пояса места рождения. Нельзя заменять город только текстовым названием без сохранения координат и timezone.

### Бацзы и единый контекст рождения

Общие helper-функции в `oracle.ts` используют согласованный контекст города, координат и часового пояса. Все личные активизации должны использовать один и тот же birth chart context.

### Летящие звёзды и Фэншуй

Летящие звёзды рассчитываются динамически по году и месяцу, а не только для 2026 года. Если годовая звезда попадает в центр или блокируется месячной звездой 5, используется месячная логика согласно текущему модулю денег.

### Личная Путешествующая лошадь

Текущая логика:

- лошадь определяется по земной ветви дня рождения;
- если лошадь является личным Разрушителем, вся активизация скрывается;
- дата должна быть днём именно личной лошади;
- обязателен час личной лошади;
- дополнительные часы могут быть Слиянием, Союзом и Сезоном;
- часы проходят фильтры пустоты и столкновений;
- исключаются часть неблагоприятных связей, Три Ша, разрушители, Земляной период и коридоры затмений;
- публикация идёт в окне до 3 дней до даты активизации.

### Вталкивание денег

Текущая логика:

- дни определяются по ветвям года и дня рождения;
- рассчитываются звёзды 1, 6 и 8, направления и сектора;
- используются фонтанчик, вентилятор и свеча;
- выбираются часы дня, Слияния, Союза и Сезона;
- дополнительно учитываются часы личного Благородного человека и Почтовой лошади;
- все часы проверяются на пустоту, столкновение с днём, месяцем и натальными ветвями;
- Полезные Боги пока не включены;
- техническое предупреждение о замене годового сектора месячным скрыто от пользователя.

### Эфемериды затмений

`eclipseEphemeris.ts` содержит локальные данные NASA на горизонт 2026-2036 годов. Для каждой связки близких событий строится единый коридор: 3 дня до первого затмения, весь интервал между событиями и 3 дня после последнего.

Эфемериды хранят точный момент максимума в UTC. При расширении западных прогнозов следует добавить API-вывод затмений, их знак, градус, лунный узел и попадание в дома натальной карты.

## 16. Типовые проблемы

### API не запускается с ошибкой `relation does not exist`

Причина: схема PostgreSQL не применена или `DATABASE_URL` указывает не на ту базу.

Решение:

```bash
pnpm --filter @workspace/db run push
```

После этого перезапустить API.

### Frontend открывается, но запросы API не работают

Проверить:

- `VITE_API_URL` задан до frontend-сборки;
- API-домен доступен по HTTPS;
- CORS разрешает домен frontend;
- reverse proxy передаёт `/api` на API;
- в браузере нет mixed-content запроса с HTTPS на HTTP.

### Clerk не авторизует пользователя

Проверить соответствие publishable и secret keys, домен Clerk, allowed origins, callback URLs и наличие `CLERK_SECRET_KEY` в API.

### Город не сохраняется

Проверить `/api/cities/search`, `/api/profile`, корректность JSON и наличие coordinates/timezone. Расчёты Бацзы и западной карты зависят от этих данных.

### После изменения `VITE_*` ничего не поменялось

Vite встраивает эти переменные во время сборки. Нужно заново выполнить:

```bash
pnpm --filter @workspace/web run build
```

и перезапустить или перепубликовать static hosting.

### В production frontend показывает старую версию

Проверить кэш CDN, timestamp сборки и содержимое `artifacts/web/dist/public`. После деплоя можно временно добавить cache-busting через новую сборку, но не менять URL API без обновления `VITE_API_URL`.

## 19. Последние функциональные изменения и важные технические примечания

Этот раздел добавлен после первоначальной подготовки файла и должен учитываться при переносе или восстановлении проекта.

### 19.1. Западная астрология и лунар

В проект добавлен модуль `artifacts/api-server/src/lib/lunarReturn.ts`. Он находит точный момент возвращения транзитной Луны к натальной эклиптической долготе Луны пользователя. Важный инвариант расчёта: Луна лунара должна находиться в том же знаке и на том же градусе, что и натальная Луна.

Расчёт лунара строится по городу проживания пользователя. Используются координаты и часовой пояс проживания. Если город проживания не заполнен, применяется город рождения, а интерфейс показывает предупреждение:

> Лунар рассчитан для города рождения. Укажите город проживания в настройках для нового расчёта.

Текущая карта лунара отображается постоянно во вкладке «Западная астрология». В «Блокноте дня» создаётся только одна автоматическая запись в дату начала нового лунара: «Начался новый лунар. Подробности во вкладке Западная астрология».

Момент лунара уточняется до секунд. Для снижения нагрузки текущий результат кэшируется на сервере на 10 минут с учётом даты рождения, времени рождения, даты расчёта, места расчёта, координат и часового пояса. При смене города проживания используется другой ключ кэша.

### 19.2. Врата Золушки

Добавлен отдельный модуль `artifacts/api-server/src/lib/cinderellaGates.ts`. Он не изменяет обычную таблицу аспектов и натальное колесо.

Натальные Врата Золушки выводятся отдельной карточкой во вкладке «Западная астрология». Транзитные Врата выводятся в «Синтезе дня». Для пользователя показываются только период действия и дата кульминации. Фазовые статусы «аспект приближается» и «аспект действует после кульминации» в интерфейс не выводятся.

После изменения схемы Врат Золушки необходимо обновлять `lib/api-spec/openapi.yaml` и выполнять codegen, чтобы синхронизировать Zod-схемы и React API-клиент.

### 19.3. Эфемериды затмений

В `artifacts/api-server/src/lib/eclipseEphemeris.ts` хранится локальный набор эфемерид солнечных и лунных затмений на горизонт 2026-2036 годов. Данные основаны на каталогах NASA. События, относящиеся к одной связке затмений, объединяются в коридор: три дня до первого события, весь интервал между солнечным и лунным затмением и три дня после последнего события.

Эфемериды используются как локальные данные без сетевого запроса во время пользовательского расчёта. Это важно для стабильной работы на VPS и других хостингах без зависимости от внешнего сервиса. При расширении периода нужно обновить сам модуль и добавить контрольную проверку дат.

### 19.4. Активизации Бацзы и Блокнот дня

В расчётах активизаций сохранены отдельные правила каждой функции. Нельзя заменять их одной общей таблицей благоприятных часов.

Для «Благородного помощника», «Вталкивания денег» и «Личной Путешествующей лошади» двухчасовки выводятся по временной линии: от `01:00-03:00` до `21:00-23:00`, а интервал `23:00-01:00` выводится последним. Порядок не зависит от силы часа или типа связи.

В «Вталкивании денег» часы проходят фильтры пустоты и конфликтов до вывода. Полезный Бог пока намеренно не используется ни в одной активизации. Личные часы Благородного человека и Почтовой лошади учитываются только после прохождения тех же строгих фильтров.

Блокнот дня формирует автоматические записи для календарных активизаций, Цветка Персика, Удачи продвижения, Благородного помощника, Вталкивания людей, Вталкивания денег, Личной Путешествующей лошади и нового лунара. Для Удачи продвижения запись создаётся в первый день нового периода, для лунара - только в дату нового возвращения. Дубликаты предотвращаются через `source` и `refKey`.

### 19.5. Порядок карточек активизаций

На странице Бацзы карточки активизаций сортируются по ближайшей дате. Сегодняшние активизации должны отображаться перед завтрашними, а завтрашние - перед более поздними. Это реализовано на frontend через вычисление порядка по `daysUntil` и дате начала периода.

Если порядок снова нарушится после изменения API, проверять нужно два места: формирование `daysUntil` в `artifacts/api-server/src/routes/systems.ts` и CSS-порядок карточек в `artifacts/web/src/pages/bazi.tsx`.

### 19.6. Мобильное пояснение «Дни трат»

В карточке «Грабитель богатства» пояснение к фразе «Дни трат» больше не использует hover-only Tooltip. На мобильных устройствах применяется нативное раскрытие `details/summary`: нажатие на «Дни трат» раскрывает текст вниз, повторное нажатие сворачивает его.

### 19.7. Раскрывающиеся таблицы западной астрологии

Таблицы «Планеты», «Дома (Плацидус)» и «Аспекты» на странице западной астрологии свернуты по умолчанию. Они раскрываются вниз по нажатию и сворачиваются повторным нажатием. Всплывающие окна для этих таблиц не используются.

### 19.8. Исправление Clerk для Render

Для совместимости production-сборки Render прямой импорт `verifyToken` из `@clerk/backend` был заменён на импорт из `@clerk/express`, который уже является рабочей зависимостью API. Если при переносе снова появляется ошибка `Could not resolve "@clerk/backend"`, нужно проверить, что в `artifacts/api-server/src/lib/auth.ts` не восстановлен старый импорт и что lockfile соответствует `package.json`.

### 19.9. Известные некритичные предупреждения

Frontend-сборка Vite может выводить предупреждения о невозможности найти исходные позиции sourcemap у UI-компонентов и о размере JavaScript-бандла более 500 kB. Сейчас это предупреждения, а не ошибки: production-сборка завершается успешно. Их можно оптимизировать отдельно через code splitting и корректные sourcemap, но для запуска проекта они не блокирующие.

## 19. Skill общего ИИ-анализа синастрии

Для будущего подключения ИИ подготовлен отдельный skill:

```text
/home/ubuntu/skills/synastry-ai-interpretation/SKILL.md
```

Skill используется только для дополнительного анализа всей уже рассчитанной синастрии. Он не пересчитывает карты, не меняет орбисы, фильтры, дома или результаты Rule of Three и не смешивается с ежедневным генератором транзитов или слоем `Entities`.

Основной интерфейс контакта сохраняет прозрачный раздельный вывод: Врата Золушки, аспекты, планеты в домах и ключевые темы 3+ указаний. Общая кнопка ИИ-анализа должна передавать модели все эти рассчитанные данные одним структурированным контекстом. Результатом является один связный литературный текст о динамике пары, а не механическая склейка отдельных карточек.

Методика анализа строится в такой последовательности:

1. Определить 3-5 главных сюжетов отношений.
2. Выделить центральное напряжение или ресурс каждого сюжета.
3. Определить психологические роли планет.
4. Учесть характер аспекта.
5. Использовать дома как жизненные сцены проявления аспекта, не повторяя их полные интерпретации подряд.
6. Объединить повторяющиеся смыслы.
7. Завершить сюжет конструктивным способом взаимодействия и дать общий вывод.

Эталонным примером для проверки качества является связка: Ваш Юпитер - оппозиция к Солнцу контакта; Юпитер пользователя в XII доме контакта; Солнце контакта в IX доме пользователя; Солнце пользователя в V доме контакта; Юпитер контакта в VI доме пользователя. Центральная тема этой связки: расширение возможностей сталкивается с правом самостоятельно выбирать путь.

Skill содержит полный образец цельной интерпретации этой связки и правила русского языка: обращение «Вы» с заглавной буквы, сохранение направленности «Ваш Юпитер» и «Солнце контакта», корректное управление падежами, отсутствие категоричных предсказаний и запрет на выдумывание отсутствующих аспектов или домов.

На текущем этапе ИИ к проекту ещё не подключён. Подключение потребует отдельного API или LLM-коннектора, серверного endpoint для передачи структурированного контекста и области вывода результата в модальном окне контакта. Skill должен передаваться модели как постоянная инструкция анализа.


### Ограничение входных данных для ИИ

Будущий endpoint общего ИИ-анализа не должен передавать модели полный внутренний объект `synastryData`. Сервер обязан заранее сформировать отдельный безопасный пользовательский payload, содержащий только данные, уже предназначенные для вывода в окне контакта: Врата Золушки, отфильтрованные аспекты, планеты в домах, Rule of Three, необходимые подписи участников, пол и направление формулировок.

ИИ не должен самостоятельно читать файлы проекта, Oracle Studio, базу данных, натальные данные, ежедневные транзиты, слой `Entities`, черновики или исключённые аспекты. Он работает только с переданным payload и не имеет права добавлять отсутствующие положения, аспекты или интерпретации. Это ограничение является обязательной частью архитектуры и skill `synastry-ai-interpretation`.


### Персонализация имени контакта

В пользовательском окне синастрии вместо обезличенного слова «контакт» следует использовать имя, присвоенное записи контакта. Интерфейс должен склонять имя по роли в предложении: «Синастрия с Ваней», «Солнце Вани», «Вы пробуждаете у Вани желание проявляться»; для имени «Милый» - «Синастрия с Милым», «Солнце Милого». Если безопасное склонение невозможно, имя не изменяется автоматически, чтобы не создавать ошибочную форму.

Это правило распространяется и на будущий общий ИИ-анализ. Имя контакта передаётся в разрешённом пользовательском payload, а skill требует использовать его вместо слова «контакт» и соблюдать падеж. Расчёты аспектов, домов и орбисов от имени не зависят.
