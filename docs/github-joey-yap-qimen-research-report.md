# GitHub-анализ материалов по Joey Yap и Qi Men Dun Jia

## Итог поиска

В открытом GitHub-поиске не найден официальный публичный репозиторий Joey Yap, QiMen Explorer или Joey Yap Research International с исходным кодом калькулятора. Найдены независимые реализации Qi Men Dun Jia, учебные заметки, TypeScript/JavaScript/Python/Go-библиотеки и проекты с AI-интерпретацией. Они полезны для сравнительного аудита, но **не являются доказательством правил Joey Yap**.

Это важное отрицательное наблюдение: если репозиторий не принадлежит официальной организации и не содержит ссылки на первичный источник, его таблицы нельзя автоматически переносить в Aether Oracle как «метод Joey Yap». Их можно использовать для поиска альтернативных алгоритмов, тестовых дат и архитектурных решений.

## Что нашли в коде

### MrJelly/QiMenDunJia

Этот проект особенно интересен для Aether Oracle как архитектурный образец. Он разделяет календарь и ядро расчёта через адаптеры, имеет варианты календарного движка и отдельные модули для `dipan`, `jiuxing`, `bamen`, `bashen` и типов карты. README заявляет поддержку точных солнечных терминов через ShouXing и совместимость с `tyme4ts`.

Полезная идея для нашего проекта — не перенос таблиц вслепую, а выделить интерфейс календарного снимка:

```text
CalendarSnapshot
  -> four pillars
  -> solar term and exact boundary
  -> day/hour mode
  -> Ju and Yin/Yang Dun
  -> Earth Plate
  -> Heaven Plate
  -> Stars, Doors, Deities
```

Это соответствует уже существующему направлению Aether Oracle: сложные поправки времени должны оставаться в календарном модуле, а `chart.ts` должен получать нормализованные данные.

### oceanjustinlin/qimen

Репозиторий ценен прежде всего порядком промежуточных этапов и форматом данных. В нём присутствуют функции/структуры, относящиеся к четырём столпам, картам, промежуточной информации и дополнительной оценке. Однако рядом с расчётами находятся AI-интерпретации и BaZi-логика. Поэтому из него можно заимствовать идею трассировки расчёта, но не готовые тексты и не правила без контрольной сверки.

Для Aether Oracle полезно добавить диагностический объект:

```text
calculationTrace = {
  calendarSnapshot,
  pillars,
  term,
  dun,
  ju,
  xunshou,
  earthPlate,
  zhiFu,
  zhiShi,
  heavenPlate,
  stars,
  doors,
  deities,
  filters
}
```

Это позволит объяснять расхождение с Mingli или Joey Yap по этапам, а не сравнивать только итоговую картинку.

### deminzhang/qimen-go

Go-репозиторий полезен как компактная независимая реализация и дополнительный источник для сравнения таблиц. Его MIT-лицензия облегчает использование идей и кода при соблюдении условий лицензии. Но в README нет основания считать его реализацией Joey Yap, поэтому он годится для cross-check, а не для выбора эталона.

### YHN Digital Qi Men

Python-проект заявляет диапазон 1900–2100, встроенные точные термины для 2026 и 2044 годов, расчёт 四柱, 局数, 值符, 值使, 九星, 八门, 八神 и Небесной/Земной тарелок. Также заявлена большая библиотека интерпретаций.

Это потенциально полезный источник контрольных дат, но есть два риска. Во-первых, README содержит рекламные формулировки, которые ещё не проверены фактическим кодом. Во-вторых, лицензия AGPL-3.0 означает, что перенос существенных частей в проект с серверным публичным доступом требует отдельной юридической проверки. Я не рекомендую копировать его тексты или код; допустимо изучать алгоритмы и сравнивать результаты.

### funan-tech-folks/nodejs-qmdj

Репозиторий скорее исследовательский и инфраструктурный. Он может быть полезен для терминологии и отдельных JavaScript-подходов, но не выглядит лучшим источником для современного календарного слоя или годовых карт.

## Связь с Joey Yap

Поиск GitHub не выявил открытого исходного кода Joey Yap. Это согласуется с тем, что официальный QiMen Explorer является закрытым продуктом, а официальные страницы описывают его как инструмент с расширениями: Lead Stem, Envoy/Lead Door, Lead Star, Season Strength, Nobleman, Horse Star, 7 Star Path, 64 Hexagrams и Progression Keywords.[1]

Независимые GitHub-проекты в основном реализуют классический или авторский QMDJ и не показывают закрытую внутреннюю логику Joey Yap. Поэтому их нельзя использовать для ответа на вопросы, которые требуют именно Joey Yap-совместимого результата:

- полный алгоритм годового `Ju` для 180 Year Charts;
- точное построение Destiny Chart;
- формула Guardian/Chief Deity;
- закрытые 7 Star Path и Zhuge Hexagram;
- точная модель Solar/Rubber/Combined времени;
- все правила Joey Yap Month Charts и Day Charts.

## Практический вывод

GitHub не дал готового «движка Joey Yap», но дал три полезных результата.

Во-первых, он подтвердил архитектурную необходимость отделить точный календарный слой от QMDJ-ядра. Во-вторых, он дал независимые реализации для дифференциального тестирования. В-третьих, он показал, что разные проекты расходятся именно в тех местах, которые уже являются проблемными для Aether Oracle: San Yuan/Ju, поздняя и ранняя Крыса, дневные и годовые режимы, Lead Star/Lead Door и дополнительные авторские слои.

Лучшие кандидаты для дальнейшей технической сверки — `MrJelly/QiMenDunJia`, `deminzhang/qimen-go`, `oceanjustinlin/qimen` и `ChesterRa/mingpan`. `YHN...Digital-Qi-Men...` полезен как источник альтернативных таблиц и интерпретаций, но его AGPL-лицензия и рекламные заявления требуют осторожности.

Следующий безопасный шаг — не перенос кода, а автоматический **differential test harness**: одна дата и час подаются в Aether Oracle и независимые движки, затем сравниваются четыре столпа, солнечный термин, Yin/Yang Dun, Ju, Earth Plate, Zhi Fu, Zhi Shi, Heaven Plate, Stars, Doors и Deities. Только совпадающие значения, подтверждённые официальными контрольными картами, могут стать основанием для изменения production-кода.
